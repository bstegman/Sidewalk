# DirectPeer Protocol (DPP) v0.1

A computer-to-computer chat protocol. Messages exist only on the two endpoints and only while a live session is open. Intermediate machines, if any, may forward encrypted packets in memory. They must not persist chat content.

## Design rules

1. Identity is a keypair, not an account.
2. Both peers must be online at the same time. There is no mailbox.
3. Application data is end-to-end encrypted before it leaves the sender.
4. Any helper (STUN, optional relay, bootstrap) must not store message payloads.
5. Clients interoperate if they follow this document, regardless of language or UI.

## 1. Identity

Each user generates a long-term **Ed25519** identity keypair.

- **Peer ID** = 32-byte Ed25519 public key, encoded as lowercase hex (64 chars).
- Display name is local-only and optional. It is not an identifier.
- Private key never leaves the device.

Address string for sharing out of band:

```text
dpp:1:<peer-id-hex>
```

Optional connection hint after first contact:

```text
dpp:1:<peer-id-hex>@<ip>:<port>
```

Example:

```text
dpp:1:8f14e45fceea167a5a36dedd4bea2543d64883e634f0f86d1d16d1dd9a441f11
```

Users exchange this string in person, by QR, email, another app, etc. That is how contacts are added. There is no directory server.

## 2. What "computer to computer" means

Preferred path:

```text
Client A  <---- encrypted TCP/QUIC/WebRTC ---->  Client B
```

Allowed helpers that do **not** store chat data:

| Helper | Role | Persistence rule |
|---|---|---|
| STUN | Tell a peer its public IP:port | Must not see payloads |
| Optional relay | Forward already-encrypted bytes when NAT blocks direct path | Memory only. Drop when the session ends. Never write payload to disk. |
| Local discovery (mDNS) | Find peers on the same LAN | Local network only |

Forbidden:

- Storing undelivered messages on a server
- Accounts, phone numbers, or a central user database
- A server that can decrypt content

Offline delivery is out of scope for v0.1. If B is offline, A cannot send. The client should show that clearly.

## 3. Transport

A client MUST support at least one of:

1. **TCP** on a chosen port (default `4747`)
2. **WebRTC data channel** (for browsers)
3. **QUIC** (optional)

All of them carry the same framed, encrypted application messages after handshake.

Noise handshake messages and Noise transport messages are not self-delimiting. On a byte stream (TCP, or a QUIC stream), send each one as its own record:

```text
uint32 BE length | Noise message
```

`length` is the number of Noise message bytes that follow. It does not include itself. Reject a length of 0, or a length greater than 65551 (65535 bytes of plaintext plus the 16-byte Poly1305 tag).

On a carrier that already keeps message boundaries (one WebRTC data-channel message, or one QUIC datagram), send exactly one Noise message per carrier message and do not add this length prefix.

NAT notes for implementers:

- Try direct connect to a known `ip:port`.
- Use STUN to learn a reflexive address and share it with the peer out of band or during an already-established session.
- Attempt UDP/TCP hole punching if you implement it.
- If direct connect fails, an optional relay may bounce **ciphertext only**. Relays are not part of the trust model.

## 4. Security handshake

Use the Noise protocol:

```text
Noise_XX_25519_ChaChaPoly_SHA256
```

Why XX: neither side needs the other's static key before the handshake starts, both sides authenticate, and static keys are transmitted encrypted.

Rules:

- The Noise prologue is empty. Do not mix in a protocol name or other prologue bytes. Two clients that choose different prologues cannot handshake.
- Each peer also has a long-term **X25519** static key used only for Noise. Bind it to the Ed25519 identity (see handshake payload below).
- Transport encryption uses that handshake's ChaCha20-Poly1305 keys. Associated data is empty.
- Rekey after 2^16 transport messages in either direction, or 10 minutes, whichever comes first. See section 6.6.
- Abort if the remote Ed25519 identity does not match the Peer ID you intended to talk to. Do this before sending `hello` or any chat.

XX has three handshake messages. Put the identity JSON only in the messages that Noise encrypts:

```text
-> e                         payload empty
<- e, ee, s, es              payload = identity JSON
-> s, se                     payload = identity JSON
```

Message 1 must be an empty payload. If it is not, disconnect. Messages 2 and 3 must each carry the sender's identity JSON. If that payload is missing, disconnect.

Handshake payload (UTF-8 JSON):

```json
{
  "proto": "dpp/0.1",
  "peer_id": "<ed25519-hex>",
  "noise_static": "<x25519-public-hex>",
  "sig": "<ed25519-signature-hex>",
  "name": "optional display name",
  "features": ["text", "typing", "receipts"]
}
```

`peer_id`, `noise_static`, and `sig` are lowercase hex. `noise_static` is the 32-byte X25519 public key used as this peer's Noise static key in this handshake. `sig` is the 64-byte Ed25519 signature over the exact UTF-8 string:

```text
dpp/0.1|noise_static=<x25519-public-hex>
```

The receiver MUST:

1. Verify `sig` with the Ed25519 key in `peer_id`.
2. Check that `noise_static` is the remote static key just received in the Noise `s` token. A signature over some other X25519 key is a failure.
3. If this connection was opened toward a particular `dpp:1:` address, check that `peer_id` is that address. Any other Peer ID is a failure.

On any failure, disconnect. Do not send chat. `name` is optional; omit it when empty, and keep it to 64 characters. `features` is optional. JSON object key order does not matter. The signature covers only the string above, not the JSON.

## 5. Framing (after Noise)

Each decrypted Noise transport plaintext is exactly one application frame. Do not concatenate frames in one plaintext.

```text
[uint32 BE length][uint8 type][payload]
```

- `length` = number of bytes after the length field (`1 + payload length`)
- The whole frame, including the 4-byte length, MUST fit in one Noise transport message. Noise limits that plaintext to **65535** bytes, so a frame of 65536 bytes is not valid. Larger messages are not allowed in v0.1 (no file transfer yet).
- `type`:

| type | name | payload |
|---|---|---|
| 0x01 | json | UTF-8 JSON object |
| 0x02 | ping | empty |
| 0x03 | pong | empty |
| 0x04 | close | optional UTF-8 reason |

Unknown types: ignore the frame, do not disconnect. A malformed JSON payload is the same: ignore that frame, do not disconnect. A failed Noise authentication means the session is broken: disconnect.

Ping every 20 seconds during which no frame has been received. Any received frame, including `pong`, shows the peer is still there. Close if no frame has been received for 60 seconds.

## 6. Application JSON messages

All chat semantics live in `type=0x01` frames.

Common envelope:

```json
{
  "v": 1,
  "id": "<uuid-v4>",
  "t": "<message-type>",
  "ts": 1730000000000
}
```

`ts` is milliseconds since Unix epoch on the sender's clock. Treat it as a hint, not truth.

### 6.1 Chat text

```json
{
  "v": 1,
  "id": "b3c1e2a0-1c4a-4f0e-9c1a-0a1b2c3d4e5f",
  "t": "msg",
  "ts": 1730000000123,
  "body": "hello",
  "reply_to": null
}
```

`body` is plain text. Max 8000 Unicode characters (code points), not 8000 bytes. If a `msg` is longer, do not display it. Reply with an `error` frame, `code` `too_large`, and stay connected.

Unknown `t` values are ignored. Do not disconnect.

### 6.2 Delivery / read receipts

```json
{ "v": 1, "id": "<new-uuid>", "t": "ack", "ts": 1730000000456, "ack_id": "<original-msg-id>", "state": "delivered" }
```

`state` is `delivered` or `read`. Receipts are optional. A client may omit them.

### 6.3 Typing

```json
{ "v": 1, "id": "<uuid>", "t": "typing", "ts": 1730000000500, "on": true }
```

If `on` is true, the other client may show "typing..." for 5 seconds or until `on: false`.

### 6.4 Presence

Sent once after handshake and on status change:

```json
{
  "v": 1,
  "id": "<uuid>",
  "t": "hello",
  "ts": 1730000000000,
  "name": "Ada",
  "status": "online"
}
```

`status`: `online` or `away`.

### 6.5 Error

```json
{ "v": 1, "id": "<uuid>", "t": "error", "ts": 1730000000600, "code": "too_large", "detail": "body exceeds 8000" }
```

### 6.6 Rekey

Either side may rekey. Send this as a normal `0x01` frame, then immediately start a new `Noise_XX_25519_ChaChaPoly_SHA256` handshake on the same connection. The sender of `rekey` is the initiator. The receiver is the responder. Use the same long-term static keys and the same identity payload rules as section 4. Chat keys change only after that handshake finishes. Wipe the previous transport keys.

```json
{ "v": 1, "id": "<uuid>", "t": "rekey", "ts": 1730000000700 }
```

Messages already encrypted under the old keys may still be in flight. Read the next record and try the old transport key first. If authentication fails, that record is the next handshake message, not a broken chat frame.

The peer with the lexicographically smaller `peer_id` SHOULD be the one that starts a rekey when the 10-minute timer fires, or when it sees the other side approach 2^16 transport messages. A peer MUST rekey before it sends a transport message at nonce 2^16. Both sides MUST accept a `rekey` from the other. Opening a fresh connection instead of rekeying on the same one is also allowed.

## 7. Session lifecycle

```text
1. User pastes or scans a dpp: address
2. Client resolves a candidate endpoint (hint, previous session, LAN mDNS, or user-entered IP)
3. Open TCP / WebRTC / QUIC
4. Noise XX handshake + identity verify
5. Send hello
6. Exchange msg / typing / ack frames
7. Either side sends close, or timeout
8. Wipe session keys from memory
```

Local history is allowed **on the user's own machine only**. The protocol does not sync history. If you store transcripts locally, encrypt them at rest with a key derived from the identity key or a user passphrase.

## 8. Local discovery (optional but useful)

On a LAN, advertise via mDNS:

- Service type: `_dpp._tcp`
- Port: listening port
- TXT:
  - `id=<peer-id-hex>`
  - `ver=0.1`

A client may auto-list nearby peers. Connecting still requires the user to accept the Peer ID (anti-spoof).

## 9. Threat model (short)

Protected:

- Eavesdroppers on the network cannot read bodies.
- A relay that only forwards Noise records cannot read bodies.
- Impersonation of a known Peer ID without the private key.

Not protected by v0.1:

- Your IP is visible to the peer on a direct connection.
- A global passive observer can see that two IPs are talking (metadata).
- Compromise of a device exposes local history and keys.
- First-contact Trust On First Use unless the user verifies the Peer ID out of band.

If IP hiding matters later, run the same protocol over Tor or I2P. Do not add that to the core spec yet.

## 10. Minimal viable client

A first client is valid if it can:

1. Generate and persist an identity keypair
2. Show a `dpp:1:<peer-id>` address
3. Listen on TCP 4747
4. Dial another `ip:port`
5. Complete Noise XX and verify Peer ID
6. Send and display `msg` frames
7. Refuse to send if not connected

That is enough for two laptops on the same network or with one side port-forwarded.
